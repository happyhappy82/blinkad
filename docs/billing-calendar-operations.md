## 날짜와 회차 규칙

**정산일 = 해당 회차의 실제 작업 종료일이 속한 달의 마지막 날짜.**

| 작업 | 정산일 |
|---|---|
| 1회차 작업이 2026-09-04 종료 | 2026-09-30 |
| 2026-09-05 연장 시작, 2회차 작업이 2026-10-04 종료 | 2026-10-31 |

- 회차마다 따로 계산한다. 입금일·연장 시작일·다음 회차 입금 요청일을 정산일로 사용하지 않는다.
- 입금/갱신 기준일, 작업 종료일, 정산일은 서로 다른 날짜다. **입금 요청 이벤트는 확인된 입금 기준일에 저장한다.** ERP·Notion의 기존 5일 전 안내 계산은 캘린더 날짜로 사용하지 않는다. 이번 캘린더 정리는 ERP 코드나 Notion 안내일 수식을 수정한 작업이 아니다.
- 입금 요청의 N회차는 **앞으로 입금받을 회차**, 정산의 N회차는 **작업을 마친 회차**다. 연장이 확정되지 않은 다음 회차는 제목에 `연장 시`를 명시하고 확정 미수금으로 취급하지 않는다.
- 납부 완료·선입금 회차 또는 종료 매장의 추가 수금 요청은 생성하지 않는다. 과거 사전 요청을 입금 요청일로 다시 등록하지 않는다.
- 3개월 선입금은 입금완료 제목에 `1~3회차`로 표시하고, 정산은 1·2·3회차 각각의 작업 종료월 말일에 잡는다. 이미 낸 회차를 다시 청구하지 않는다.
- ERP `cycleEndDate`는 실제 마지막 작업일 대신 다음 회차 경계일을 담는 사례가 있다. 예: 주도락 8/12~9/11 운영, ERP 종료 기준일 9/12. 기존 설명은 이를 `회차 종료 기준일(ERP 등록)`으로 명시했다.
- 2026-09-06 반영한 23건은 이 경계 차이가 정산월을 바꾸지 않았다. 향후 월초·월말 경계 계약에서는 실제 작업 종료일을 계약/운영 기록과 확인하고, ERP 경계일을 그대로 실제 종료일로 단정하거나 일괄 하루 차감하지 않는다.

## 제목과 설명

제목은 항상 `[회차 + 일정 종류] 매장명`으로 시작한다.

| 종류 | 예시 |
|---|---|
| 계약 시작 | `[1회차 계약 시작] 매장명` |
| 입금완료 이력 | `[1회차 입금완료 기록] 매장명` |
| 선입금 | `[1~3회차 선입금 완료] 매장명` |
| 입금 요청 | `[4회차 입금 요청] 매장명` |
| 연장 시 입금 요청 | `[2회차 입금 요청 · 연장 시] 매장명` |
| 작업비 정산 | `[3회차 정산] 매장명` |

설명에는 해당 유형에 필요한 다음 정보를 넣는다.

- 매장명, 대상 회차, 일정일, 입금·갱신 기준일 또는 회차 시작·종료일, 별도 정산일.
- 용역비, 실제 광고 집행비, 합계와 VAT 포함/별도 기준. 광고비를 용역 매출·순수익과 합치지 않는다.
- 입금완료·선입금·갱신 미확정·과거 이력 등 상태. 갱신 금액이 미확정이면 기존 금액은 참고값으로 표시한다.
- 외부 정산금이 있으면 참고금액과 실제 지급 여부 확인이 필요함을 구분한다.
- ERP 원본 종류, 기준일, 청구관리·정산관리 링크. 담당자는 확인된 경우에만 추가한다.
- 실제 송금, 고객 안내 발송, ERP 입금완료/정산완료 처리는 일정 등록과 별개다.

## 이벤트 저장과 중복 방지

- 종일 이벤트: `start.date`는 표시 날짜, `end.date`는 다음 날짜로 저장한다. 자정 UTC 시간 이벤트로 바꾸지 않는다.
- 시간 점유 없음: `transparency=transparent`. 기본 공개 범위 사용.
- 이벤트 참석자를 추가하지 않는다. 팀 공유는 캘린더 권한으로 처리한다.
- 현재 기본 알림은 없음: `reminders.useDefault=false`, 별도 override 없음. 추가 알림·초대가 필요하면 해당 요청 범위에서 설정한다.
- 무기한 반복을 생성하지 않는다. 확인된 계약 회차와 ERP에 표시된 다음 갱신 확인 일정까지만 반영한다.
- 원본 ID는 `extendedProperties.private.blinkadErpSourceId`에 보관한다. 종류는 `blinkadErpType`, 최초 반영일은 `blinkadImportDate`에 있다.
- 2026-09-07 이후 입금 요청 이벤트는 `blinkadErpType=입금예정`(기존 내부 식별값 유지, 화면 명칭은 `입금 요청`), `blinkadPaymentScheduleRule=due_date_only`, `blinkadPaymentDueDate=실제 입금 기준일`을 저장한다. 기존 `request-...` 원본 ID는 중복 방지를 위해 유지한다. 삭제된 요청은 최신 변경 원장과 대조해 재생성하지 않는다.
- 정산에는 `blinkadErpCycleEndDate`, `blinkadSettlementDate`, `blinkadSettlementRule=completion_month_end`를 함께 보관한다.
- 예시 원본 ID: `contract-매장명`, `request-매장명-2`, `end-매장명-1`. 원본에서 받은 문자열을 기준으로 비교하며 매장명만으로 매칭하지 않는다.
- 신규 이벤트 ID는 기존 실행기에서 `blinkad` + 원본 ID의 SHA-256 앞 40자리로 만들었다. 주도락 테스트를 정식 전환한 1건은 기존 Google 이벤트 ID를 유지했으므로 해시만 보고 재생성하지 않는다.
- 변경 전 대상 캘린더 전체를 조회하고 원본 ID로 매칭해 기존 이벤트를 수정한다. 제목 변경·정산 날짜 이동을 신규 이벤트 생성으로 처리하지 않는다.
- 사용자나 팀원이 추가한 별도 일정은 이번 관리 원본과 식별자가 일치하지 않으면 변경하지 않는다.
- 변경 전/후 원장과 비교 결과를 저장하고, 날짜·제목·회차·설명·금액·알림·색상·식별자·중복을 검증한다. 제목만 변경하는 작업은 나머지 필드를 보존한다.
